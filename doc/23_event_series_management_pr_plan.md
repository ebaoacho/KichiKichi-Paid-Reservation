# イベント開催回管理 PR 計画・レビュー基準

## 1. 目的

現在の Event Reservation はイベントを表す親データを持たず、開催枠、予約、ホールドを単一イベントとして扱っている。本計画では「イベント開催回」を導入し、次を実現する。

- 管理者がイベント予約タブでタイトルと開催日を指定して新しいイベントを作成できる。
- 既存イベントと新しいイベントの予約、売上、残席、CSVが混在しない。
- 過去イベントの内容と予約実績を管理画面から確認できる。
- 公開ショートコードと既存の決済・キャンセル導線を維持する。
- 既存データを「キチキチBIGオムライスイベント」として安全に移行する。

実装はPR 1からPR 5の順に行う。各PRは、直前のPRまでが入った状態でも既存のイベント予約を停止させないことを原則とする。

## 2. 確定要件

### 2.1 既存イベント

既存のイベント枠、予約、ホールド、監査ログはすべて次のイベントにまとめる。

| 項目 | 値 |
| --- | --- |
| タイトル | キチキチBIGオムライスイベント |
| 開催期間 | 2026-07-11から2026-07-19 |
| 実際の開催日 | 2026-07-11、2026-07-12、2026-07-14、2026-07-18、2026-07-19 |
| 単価 | USD 50／人 |

開催期間は最初の枠の日付と最後の枠の日付から表示する。期間内でも既存枠がない日を新たに追加してはならない。

### 2.2 新しいイベント

- 単価は既存イベントと同じ `KKPAY_EVENT_AMOUNT = 50`、通貨は `usd` とする。
- 管理画面では料金を編集させない。
- 管理者はタイトル、開催日、開催時間、枠ごとの定員を設定できる。
- 初期時間は11:00、12:30、14:00、初期定員は8名とする。
- 複数の開催日と時間枠を登録できる。
- 同時に予約受付中にできるイベントは1件だけとする。

### 2.3 イベント状態

| 状態 | 意味 | 許可する遷移 |
| --- | --- | --- |
| `draft` | 作成・編集途中。非公開 | `open` |
| `open` | 顧客予約を受付中 | `closed`、`archived` |
| `closed` | 一時停止。非公開 | `open`、`archived` |
| `archived` | 開催終了。履歴のみ | なし |

`archived` は取り消し不可とする。受付開始後に作成済みのホールドがある場合、受付状態だけを理由に決済成功後の予約確定を拒否してはならない。

## 3. データ構造

```text
kkpay_events
    id
      |
      +-- kkpay_event_slots.event_id
              |
              +-- kkpay_event_holds.slot_id
              +-- kkpay_event_reservations.slot_id
                         |
                         +-- kkpay_event_reservation_events.reservation_id
```

予約とホールドは既存の `slot_id` を維持する。イベントとの関係は枠を経由して取得し、決済済みデータの識別子を変更しない。

`kkpay_events` の想定列は次のとおりとする。

| 列 | 型・制約 | 用途 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED、主キー | イベントID |
| `title` | VARCHAR(200)、NOT NULL | イベントタイトル |
| `unit_amount` | INT UNSIGNED、NOT NULL | 1名あたりの金額 |
| `currency` | VARCHAR(3)、NOT NULL | `usd` |
| `status` | VARCHAR(20)、NOT NULL | イベント状態 |
| `created_at` | DATETIME、NOT NULL | 作成日時 |
| `updated_at` | DATETIME、NOT NULL | 更新日時 |

`kkpay_event_slots` には `event_id BIGINT UNSIGNED NOT NULL` を追加し、枠のユニークキーを `(event_id, event_date, event_time)` に変更する。

- [ ] PR途中でも現在の予約、決済確認、Webhook、キャンセルが動作する。
- [ ] 移行前後で予約件数、人数、金額、状態が一致する。

### 4.2 競合とトランザクション

- [ ] ホールド作成と予約確定のトランザクション、`SELECT ... FOR UPDATE`を維持している。
- [ ] ロック後に、対象枠が対象イベントに所属することを再確認している。
- [ ] 二重送信、ブラウザ確認とWebhookの競合、Cron処理に対して冪等である。
- [ ] 同時に2件のイベントを `open` にする競合をService層で防いでいる。

### 4.3 セキュリティ

- [ ] 公開AJAXで `kkpay_nonce` を検証している。
- [ ] 管理AJAXでnonceと `manage_options` を検証している。
- [ ] クライアントの `event_id` や `slot_id` を信用せず、DBで所属関係を検証している。
- [ ] SQL値に `$wpdb->prepare()` を使用している。
- [ ] CSVへ追加する文字列列にもCSVインジェクション対策がある。

### 4.4 金額・Stripe・返金方針

- [ ] 単価がUSD 50／人で統一され、クライアント値から決定されない。
- [ ] PaymentIntent metadata、ホールド、予約、枠、イベントが一致する。
- [ ] Webhookの署名検証、時刻許容、冪等処理を維持している。
- [ ] 顧客・管理者キャンセルからStripe Refund APIを呼んでいない。
- [ ] `charge.refunded` は外部返金の同期だけに使用している。

### 4.5 日時・履歴・コード構成

- [ ] 日時処理で `Asia/Tokyo` を明示している。
- [ ] 開催期間は枠の `MIN(event_date)` と `MAX(event_date)` から求めている。
- [ ] 過去イベントのタイトル、枠、予約実績が後の編集で変質しない。
- [ ] DBアクセスはRepository、業務ルールはService、入力検証はValidator、レスポンスはControllerにある。
- [ ] Service／Repositoryの失敗は `WP_Error` で返している。

## 5. PR 1：イベントマスタと既存データ移行

### PRタイトル案

`feat: イベント開催回マスタと既存イベントの移行処理を追加`

### 目的と変更範囲

既存コードの読み取り動作を変えずにイベント親マスタを追加し、既存データを1つの開催回へ関連付ける。

- `kkpay_events` テーブルを `dbDelta()` で追加する。
- `kkpay_event_slots.event_id` と新しいユニークキーを追加する。
- `KKPAY_Event_Repository` を追加する。
- `schema_is_missing()` に新テーブルと必須列を追加する。
- Activatorへ冪等な既存イベント移行処理を追加する。
- 固定日程のシードは既存イベント移行に必要な場合だけ実行する。

### 移行仕様

1. 既存枠が存在し、`event_id` が未設定なら移行対象とする。
2. 「キチキチBIGオムライスイベント」を移行先として1件だけ作成する。
3. `unit_amount = 50`、`currency = 'usd'` を設定する。
4. 旧Option `kkpay_event_reservation_status` の値を状態へ引き継ぐ。
5. 既存の全枠へ移行先 `event_id` を設定する。
6. 予約、ホールド、監査ログはIDを変えず、枠経由で同イベントに所属させる。
7. 移行完了を検証してからDBバージョンを更新する。

### PR 1 レビュー項目

- [ ] `CREATE TABLE` と `dbDelta()` を使用している。
- [ ] 新テーブル、必須列、インデックスをスキーマ検査へ追加している。
- [ ] 新規環境と既存環境の両方でユニークキーが正しい。
- [ ] 移行を複数回実行してもイベントが重複しない。
- [ ] 既存枠のID、日付、時刻、定員、状態が変化しない。
- [ ] 7月13日、15日、16日、17日などの枠を追加しない。
- [ ] 予約、ホールド、監査ログを削除または再作成しない。
- [ ] 移行途中で失敗しても次回実行で安全に再開できる。
- [ ] 更新前後で枠数、予約数、人数、合計金額が一致する。
- [ ] 既存予約コードで照会とキャンセルができる。
- [ ] 再有効化してもイベントや枠が増えない。

### 完了条件

既存の全枠が1件の「キチキチBIGオムライスイベント」に関連付けられ、既存の公開・管理機能が変更前と同様に動作すること。

## 6. PR 2：イベント単位のバックエンド処理

### PRタイトル案

`refactor: イベント予約処理を開催回単位に分離`

### 目的と変更範囲

- イベントの作成、更新、取得、状態遷移をRepository／Serviceへ追加する。
- 枠、予約、ホールド、残席、売上の取得に `event_id` 条件を追加する。
- `open` イベント取得処理を追加する。
- 受付開始前の検証を追加する。
- 公開枠取得とホールド作成で、枠が現在の `open` イベントに属することを検証する。
- `archived` 時のHard Closeを当該イベントの未決済ホールドだけに限定する。

### PR 2 レビュー項目

- [ ] 枠、予約、ホールド、残席、売上のすべてにイベント境界がある。
- [ ] イベントAの予約人数がイベントBの残席へ影響しない。
- [ ] Repositoryの無条件一覧取得が管理画面から使われ続けていない。
- [ ] 過去イベントの枠IDでホールドを作れない。
- [ ] 状態遷移を画面ではなくService層で制御している。
- [ ] 同時受付1件の制約がサーバー側で保証される。
- [ ] `archived` の再開を拒否する。
- [ ] Hard Closeが他イベントのホールドを処理しない。
- [ ] 受付停止直前に作成された決済成功済みホールドを確定できる。
- [ ] ブラウザ確認とWebhook確認が冪等である。

### 完了条件

すべてのイベント予約処理が開催回を識別し、異なるイベント間でデータや状態が混ざらないこと。

## 10. PR間の依存関係とマージ順

```text
PR 1: DB・既存データ移行
  |
  v
PR 2: バックエンドのイベント境界
  |
  v
PR 3: 管理画面
  |
  v
PR 4: 公開予約・Stripe・メール
  |
  v

```

- PR 2はPR 1のスキーマを前提とする。
- PR 3とPR 4はPR 2のService／Repository APIを前提とする。
- PR 5はPR 1からPR 4の本番反映と移行確認後に行う。
- 一時的な互換コードには削除予定のPR番号を記載する。

1. 既存イベントが「キチキチBIGオムライスイベント」として1件だけ表示される。

4. 新しいイベントを下書きで作成し、複数の日付と時間枠を保存できる。
5. 下書きイベントが公開ページに表示されない。

8. USD 50×人数のPaymentIntentが作成され、予約を確定できる。

## 12. 今回の対象外

- イベントごとの料金変更
- 複数イベントの同時受付
- 公開ページで顧客がイベント自体を選択する機能
- イベント予約の多言語化
- イベント間で予約や決済を移動する機能
- 本システムからイベント予約を返金する機能

これらが必要になった場合は、予約時の単価スナップショット、公開URL設計、同時受付時のイベント選択、メール文言管理を別設計として追加する。
